# SeekVec 性能与质量报告

> 正式赛题 2.4 / 3.2 的实测结果。所有数字来自**真实运行应用**（浏览器端推理 → HTTP → seekdb），原始数据随仓库提交。
> 复现命令见 [复现.md](复现.md)；模型/量化背景见 [模型与量化.md](模型与量化.md)；完整架构见 [架构.md](架构.md)；瓶颈定位与深度优化过程见 [性能优化分析.md](性能优化分析.md)。

## 0. 最终结果（2026-10-27 深度优化后）

> 主矩阵：`docs/benchmarks/matrix-2026-10-27/`（4 配置 × ABBA × 5 正式轮 + 1 预热，高优先级进程、低干扰窗口）；消融与增量导入：`docs/benchmarks/optimization-2026-10-27/`。
> 默认参数：**batch=32；WASM threads 按硬件自适应（28 核→16，8 核→8，可用 `?threads=` 固定）**。白天最终矩阵固定 threads=8 以便与历史数据复现；优化含清理批量化、集合句柄缓存、增量导入跳过未变块、UTF-8 字节长度分桶。严格消融见[性能优化分析 §10](性能优化分析.md)：threads8 对 threads4 约 −20%，batch32 对16 仅约 −3%，batch48/64 无进一步收益；因此 6.93→2.53s 是组合收益，不可全部归因于 batch/threads。

| 配置 | 实际后端/dtype | 模型体积 | 向量化吞吐 | seekdb 检索 p50 | 端到端 p50 | Recall@5 | nDCG@10 |
|---|---|---|---|---|---|---|---|
| **FP32 + WASM（基线）** | wasm/fp32 | 95.29 MB | **56.0 chunks/s**（导入 3.06 s） | 2.7 ms | 23 ms | 0.5642 | 0.7651 |
| **INT8(q8) + WASM** | wasm/q8 | **24.45 MB（3.90×）** | **75.5 chunks/s**（导入 2.53 s） | 2.8 ms | **18 ms** | **0.5744** | **0.7659** |
| **FP16 + WebGPU** | webgpu/fp16 | 47.94 MB | **485.1 chunks/s**（导入 1.25 s） | 2.2 ms | 23 ms | 0.5642 | 0.7652 |
| INT8 + WASM 冷启动 | wasm/q8 | 24.45 MB | 导入 2.67 s + 模型加载 453 ms | 2.9 ms | 21 ms | — | — |

> 官方建议表的组合口径：量化前基线 = FP32+WASM；INT8 = q8+WASM；FP16 = fp16+WebGPU（每个后端起一个量化代表）。未额外跑 INT8+WebGPU / FP16+WASM 四象限；q8+WebGPU 实测明显慢，故不纳入主表。

- 环境噪声说明：同一代码在后台高负载时可慢 2–3 倍；最终矩阵用高优先级进程跑，仍保留中位数/IQR 和原始数据。

## 1. 优化前基线（2026-10-26，历史数据）

- 在固定语料（120 篇 / 120 chunks）、10 条查询、Chrome/Chromium 153（WebGPU 可用：NVIDIA Lovelace）、seekdb 1.4.0 上完成 6 组配置 × ABBA × 5 正式轮（+1 预热轮）：
  - **INT8(q8)+WASM vs FP32+WASM**：导入总耗时 **9.47 s → 6.93 s（−26.8%）**，文档向量化吞吐 **18.4 → 28.4 chunks/s（+54%）**，模型总体积 **95.29 → 24.45 MB（3.90× 压缩）**；当前质量复测为 **+1.02pp Recall@5 / +0.0008 nDCG@10**，通过质量门。
  - **FP16+WebGPU vs FP32+WASM**：导入总耗时 **9.47 s → 3.38 s（−64.3%）**，向量化吞吐 **18.4 → 202.4 chunks/s**；模型总体积 95.29 → 47.94 MB；质量与 fp32 持平（ΔR@5 0.00pp / ΔnDCG@10 +0.0001）。
  - **优化前后（同一 q8+WASM）**：batch 16 vs batch 1 导入 **9.30 s → 6.93 s（−25.5%）**；仅末批刷新 vs 每批刷新 **11.42 s → 6.93 s（−39.3%）**。
  - 查询端到端中位数 **28–36 ms**（向量化 8.9–13.9 ms + HTTP 13.5–15.1 ms + seekdb 检索 2.2–2.7 ms + 渲染/调度），冷启动模型加载 **722 ms**（下载 359 ms + 初始化 357 ms，本地静态资源口径）。
- 双质量口径均通过质量门：Node（精确余弦）与浏览器（真实 seekdb 检索链路）。

## 4. 分阶段耗时（真实浏览器链路，p50 / IQR，单位 ms）

> 来源：`docs/benchmarks/matrix-2026-10-26/phase-aggregate.md`（由 12 次调用的 `raw.json` 二次统计；每配置 12 个正式轮；阶段值为各轮 p50 的跨轮中位数）。

### 4.1 导入（120 篇 / 120 chunks，每轮完整导入；含按 source 清理陈旧块）

| 配置 | read | chunk | doc.embed 合计 | doc.write 合计 | index.refresh 合计 | cleanup 合计 | **导入总耗时** | 导入墙钟 | docs/s |
|---|---|---|---|---|---|---|---|---|---|
| fp32-wasm | 272.6 | 1.2 | 6515.0 | 1028.5 | 559.2 | 1580.6 | **9470.4** | 9693.0 | 12.7 |
| q8-wasm | 228.3 | 1.0 | 4225.7 | 916.3 | 556.5 | 1377.9 | **6929.7** | 6954.0 | 17.3 |
| fp16-webgpu | 219.9 | 1.1 | 592.8 | 974.2 | 607.5 | 1510.7 | **3377.2** | 3409.5 | 35.5 |
| q8-wasm-batch1 | 199.8 | 1.0 | 4634.9 | 3023.9 | 507.5 | 1445.4 | **9296.8** | 9326.5 | 12.9 |
| q8-wasm-refresh-each | 215.9 | 1.1 | 4183.7 | 5170.4 | 4771.4 | 1512.4 | **11423.7** | 11625.0 | 10.5 |
| cold-q8-wasm | 239.2 | 1.2 | 4335.2 | 944.2 | 557.3 | 1440.5 | **7070.6** | 7760.0 | 17.0 |

- 单批 embedding（8 批/轮）：fp32 **860.5**、q8 **558.3**、fp16+WebGPU **71.5**、batch1（120 批）**38.3**、refresh-each **556.7**、cold-q8 **570.1** ms。
- 单次索引刷新约 **507–607 ms**；`refresh=last` 每轮 1 次，`refresh=each` 每轮 8 次（合计 4771 ms，占总耗时 42%）。
- 写入单批（8 批/轮）：batch16 约 **42 ms/批**；batch1 为 120 次 HTTP（合计 3024 ms），体现批处理对网络/事务开销的优化。
- `cleanup` 为“按 source 清理陈旧 chunk（list + delete + refresh）”，是为保证连续导入一致性的额外防护；在 120 篇全量写入场景占导入耗时 ~1.4–1.6 s。当前实现按文件清理，后续可按批合并/仅变更时触发以进一步降低。

| 配置 | query.embed | query.http | seekdb db.search | query.e2e |
|---|---|---|---|---|
| fp32-wasm | 11.6 (1.4) | 12.9 (3.2) | 2.2 (0.9) | **32.5 (7.0)** |
| q8-wasm | 9.0 (1.5) | 13.5 (3.4) | 2.2 (1.1) | **28.0 (4.0)** |
| fp16-webgpu | 13.9 (2.0) | 15.0 (2.1) | 2.7 (0.7) | **35.0 (4.8)** |
| q8-wasm-batch1 | 8.8 (0.9) | 13.5 (1.4) | 2.2 (0.2) | 28.0 (3.6) |

- HTTP（含 Vite 代理 + Express + JSON）约 **13–15 ms**，是查询链路中最大固定开销；seekdb 自身检索只有 **2.2–2.7 ms**。
- WebGPU 的查询向量化（14 ms）比 q8/WASM（9 ms）略慢，但文档批向量化快 6–8 倍，适合导入主导的场景；小查询延迟以 WASM 更优。
- 混合检索（带 keyword，20/60 质量查询）由 seekdb 库内 RRF 完成，端到端与纯向量在同一量级；质量评测中已按 mode 区分。

### 4.3 模型下载与加载（首跑 vs 预热）

| 口径 | model.download | model.init | model.total |
|---|---|---|---|
| q8+WASM 冷启动（每轮清缓存，5 轮 p50 中位） | **358.7 ms** | **357.2 ms** | **722.3 ms** |
| q8+WASM 预热（浏览器缓存命中，首次计入轮） | 86.8 ms | 618.6 ms | 705.4 ms |
| fp16+WebGPU 预热（首次计入轮） | 387.2 ms | 662.3 ms | 1049.5 ms |
| fp32+WASM 预热（首次计入轮） | 930.6 ms | 1234.9 ms | 2165.5 ms |

- 本环境模型文件由本地静态目录提供（可离线复现）；`model.download` 因此代表本地加载（冷/热缓存差异），真实网络下载（HF/mirror）取决于网络，可用同一 `?models=remote` 开关复测，报告不将本地数字宣传为公网下载速度。
- 预热行的 `model.init`（618.6 ms）高于冷启动行（357.2 ms）属首轮加载/上下文创建波动（预热行 n=2、冷启动 n=12），因此首跑/预热只比较 download 与总耗时的量级，不作严格因果推断；跨配置比较以 cold-q8-wasm 为主。
- 结论：q8 冷启动加载 ~0.72 s；预热后浏览器缓存使下载阶段降到 ~0.09 s，但 ORT session 初始化仍有 ~0.6 s（可通过复用已加载 page 避免）。

## 6. 优化前后对比（2.4）

| 优化项 | 优化前 | 优化后 | 结果（同 q8/WASM、同语料） |
|---|---|---|---|
| **批处理**（embedding + 写入） | batch=1：导入 **9.30 s**，写入 3.02 s（120 次 HTTP） | batch=16：导入 **6.93 s**，写入 0.92 s（8 次 HTTP） | **−25.5%** 导入耗时；写入开销 −70% |
| **索引刷新策略** | refresh=each：导入 **11.42 s**，刷新 8 次共 4.77 s | refresh=last：导入 **6.93 s**，刷新 1 次 0.56 s | **−39.3%** 导入耗时；刷新开销 −88% |
| **模型量化**（WASM） | fp32：导入 **9.47 s**，模型 95.29 MB | q8：导入 **6.93 s**，模型 24.45 MB | 导入 **−26.8%**，向量化吞吐 +54%，体积 3.90×；当前质量复测 +1.02pp R@5 |
| **后端**（WebGPU + fp16） | q8+WASM：导入 6.93 s，向量化 28.4 chunks/s，e2e 28.0 ms | fp16+WebGPU：导入 **3.38 s**，向量化 **202.4 chunks/s**，e2e 35.0 ms | 导入 **−51.3%**，向量化 **−86% 耗时**；小查询 e2e +25%（适合导入主导；官方也要求 WebGPU 优先） |
| **确定性 ID + upsert** | 重复导入可能重复分块 | 重复导入 count 不变（幂等） | 同一文件两次导入后条目数不变（e2e 验证） |
| **集合回填 + activeCollection** | 刷新后集合清单丢失、检索静默无结果 | 启动回填并恢复选中集合 | 刷新后直接可检索（e2e 验证） |
| **陈旧块清理**（一致性） | 文件改短/改名后旧 chunk 残留 | 按 source 清理 + refresh | 文件改名/变短后检索结果与当前知识库一致（e2e 验证） |
| **HTTP/模型资源同源** | ORT 跨源 8090 + Vite `?import` 500 | 同源 `/ort/` + 绝对 URL | dev/preview/build 全链路 WASM 可用（修复阻断） |

- 优化对比的绝对值受本机负载/容器影响，但 ABBA + 5 轮中位数 + IQR 已尽量控制；同一配置正逆序差异见 `matrix-raw.json`。
- `cleanup`（一致性防护）在基准中占约 1.4–1.6 s/120 篇；后续可合并清理请求、仅变更时触发，进一步降低导入总耗时（当前不将其计入优化收益，保持口径诚实）。

## 7. 稳定性、偏差与限制

1. **ABBA 与波动**：同配置正/逆序调用存在 ±5–10% 波动（如 q8-wasm 导入总耗时正序 6776→7219 ms、逆序 7636→8331 ms，中位 6929 ms），原因包括主机后台容器（同机 19 个容器）、浏览器 JIT/GC、Docker IO。报告用中位数+IQR，不宣称毫秒级绝对精度。
2. **冷/热口径**：冷启动清空 user-data-dir/CacheStorage 后重新加载；本地模型资源使“下载”阶段偏短，公网下载会显著更慢，未将本地数字当作网络实测。
3. **WebGPU**：WebGPU 推理端在本机可用（NVIDIA Lovelace）；不同机器/驱动可能不可用，脚本会记录实际后端并标记降级，不会静默伪装。
4. **fp16 质量**：Node CPU 上 ORT 上采样为 fp32；浏览器 WebGPU 链路实测与 fp32 持平。
5. **质量集规模**：60 查询/单标注人，用于相对比较；绝对 Recall 水平受自建语料影响，不作为通用 benchmark 结论。
6. **数据库检索延迟**：seekdb 侧仅 2.2–2.7 ms；端到端主要成本在 HTTP 与浏览器调度（13–15 ms + 渲染），这与“端侧 + 本地 server”架构一致，报告中明确拆分。
