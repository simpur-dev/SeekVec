# 性能瓶颈定位与深度优化（2026-10-27）

> 目标：回答“到底哪里慢、负担来自哪里”，并记录本轮底层优化与实测前后值。原始数据在 `docs/benchmarks/optimization-2026-10-27/` 与 `docs/benchmarks/matrix-2026-10-27/`。
> 官方 3.2 最终汇总表见 [性能与质量报告](性能与质量报告.md)。

## 1. 测量条件与重要前提

- 机器：Windows 11 · i7-14700HX（28 逻辑核）· 16GB · NVIDIA Lovelace；浏览器 Chromium 153（无头）；seekdb 1.4.0（Docker，2882）。
- 语料：`data/perf` 120 篇 / 120 chunks；查询 10 条；nResults=10；每格 5 正式轮 + 1 预热，ABBA；报告 p50/IQR。
- **主机负载会显著影响绝对数字**：同一份代码在系统空闲（CPU 1%）时导入 ~3.56s，在后台 Edge/DSH/其它容器高负载（CPU 39–80%）时可到 4.5–6.5s；单轮甚至出现 9–33s（batch=1）。
  - 因此本文把“控制条件下的中位数”和“高压下的 IQR”分开；最终报告保留中位数 + IQR，并明确环境噪声。
  - 高负载进程实测：24 个 msedge 进程、DSH Harness、Docker Desktop 等；压测前应关闭无关负载。

## 2. 瓶颈定位（按阶段占比）

### 2.1 优化前（2026-10-26 矩阵，q8 + WASM，batch=16 / threads=4）

| 阶段 | p50 | 占导入总耗时 |
|---|---|---|
| 导入总耗时 | 6.93 s | 100% |
| `doc.embed`（8 批 embedding） | 4.23 s | ~61% |
| 逐文件 cleanup（120 次 list + 删除 + 刷新） | 1.38 s | ~20% |
| `doc.write`（8 次 HTTP/DB 写入） | 0.92 s | ~13% |
| `index.refresh`（末批 1 次） | 0.56 s | ~8% |
| `doc.read` + `doc.chunk` | ~0.23 s | ~3% |

结论：**embedding 是第一大头，逐文件 cleanup 是第二大头，写入/刷新次之**；查询端 resolve 与 HTTP 也有固定开销。

### 2.2 优化后（控制条件，q8 + WASM，batch=32 / threads=8）

| 阶段 | p50 | 说明 |
|---|---|---|
| 导入总耗时 | **3.56 s**（−49%） | 空闲窗口 5 轮中位数 |
| `doc.embed`（4 批） | 2.17 s | batch 32 + 8 线程（t8/b32 消融） |
| `doc.write`（4 次） | 0.67 s | 写请求数减半 |
| `index.refresh`（1 次） | 0.71 s | seekdb 全量刷新，固定成本 |
| `doc.read` + chunk | ~0.17 s | 120 个小文件顺序读取 |
| cleanup | ~0 | 新建集合跳过清理；复用集合一次 list 完成 |

### 2.3 默认 WebGPU 路径（auto → fp16）

| 阶段 | p50 |
|---|---|
| 导入总耗时 | **1.77 s**（3 轮，空闲窗口） |
| `doc.embed` | 0.42 s（约 202 chunks/s） |
| `doc.write` | 0.47 s |
| `index.refresh` | 0.71 s（占总耗时 ~40%） |
| 查询端到端 | 30.0 ms |

结论：有 WebGPU 时 embedding 不再是瓶颈，**seekdb 索引刷新变成最大固定成本**；没有 WebGPU 时 WASM q8 embedding 仍是主瓶颈。

### 2.4 查询链路（q8/WASM）

| 分段 | 优化前 | 优化后/说明 |
|---|---|---|
| server `resolveMs`（每次 getCollection） | **3.3–4.2 ms** | **0.01 ms**（集合句柄缓存命中） |
| server `dbMs`（seekdb search） | 1.7–2.4 ms | 1.7–2.5 ms（库内检索本身很快） |
| server 总耗时 | 5.3–5.8 ms | **2.1–2.6 ms** |
| 浏览器 `query.http`（含 Vite 代理） | 13–16 ms | 13–20 ms（dev 代理是固定开销） |
| `query.embed` | 6–9 ms | 5–9 ms |
| 端到端 p50 | 28–32 ms | 28–32 ms |

## 3. 逐层根因分析

### 3.1 应用/导入层（`web/src/ingest/ingestText.ts`）

1. **旧清理逻辑是 O(文件数) 次 HTTP**：每个文件 `listDocumentIds(source)` → 计算 stale → 删除。120 文件 = 120 次往返（实测 1.38s）。而且新建集合时也执行（空集合仍 120 次请求）。
2. **默认批大小/线程保守**：batch=16、WASM 线程 4；120 chunks 需要 8 批 embedding + 8 次写入。
3. **重复导入全量重算**：同一个文件再次导入仍会重新 embedding 全部 chunk（尽管 id 不变）。
4. **批内 padding 浪费**：embedding batch 按文件顺序组成，短文本被同批最长文本 padding；对长度差异大的语料有浪费（本轮测试语料长度接近，length bucketing 收益不显著，但保留该策略）。

### 3.2 推理层（Transformers.js / ONNX Runtime Web）

- WASM q8：120 chunks 约 2.17s（batch32/threads8），约 55 chunks/s；瓶颈是 CPU 矩阵乘 + tokenizer + padding。
- WebGPU fp16：同数据约 0.42s（~202 chunks/s），但查询小 batch 的调度开销略高（query.embed 9–17ms）。
- 8 线程明显优于 4：t8b32 的 embedding 总时间约 2.17s，t4b32 约 3.0s；再增大到 batch64 可到 ~2.19s embedding / 3.57s 导入，但单条大 INSERT 有 seekdb 30s 超时风险，故默认选 32。
- 未采用：Web Worker/`env.backends.onnx.wasm.proxy`（可降低主线程卡顿，但可能增加通信延迟）、token-budget 动态批、ort session graph optimization 细调。

### 3.3 Server/seekdb 层（`server/src/db/collections.ts`、`routes/search.ts`）

- `getCollection` 每个检索请求都重新取集合元数据（describe/schema），占用 3.3–4.2ms；seekdb 检索本身仅 1.7–2.5ms。
- 优化：集合句柄缓存（30s TTL，client 代际失效，创建/删除主动失效）；resolve 降到 0.01ms。
- `refresh_index` 是 seekdb 全量索引刷新，实测 0.6–0.7s；官方要求导入后刷新才可检索，当前只在最后一批刷新一次，无法直接删除。
- 写入：batch32 每次 HTTP/DB 约 0.17s；batch64 减半请求但大 SQL 有超时风险。

### 3.4 环境层

- 同一配置在 CPU 1% 与 80% 下的导入中位数差异可达 2–3 倍；batch=1 单轮 33s 是极端调度/IO 抖动。
- 这不是代码慢的证明；报告用中位数、IQR、ABBA 降低影响，并建议压测时关闭 Edge/其它容器/DSH 重负载。

## 4. 本轮落地优化（代码级）

| 优化 | 实现 | 实测收益 |
|---|---|---|
| 清理批量化 + 新集合跳过 | `GET /api/documents?withSource=1` 一次返回全部 id+source；`ingestText.ts` 内存对比后一次批量删除；created=true 完全跳过 | 旧 1.38s → 新路径 ~0；不再有 120 次 list |
| batch 16→32 | `BATCH_DEFAULT=32`（URL 可覆盖） | 写入请求 8→4；t8b32 vs t8b16 导入 4.25s vs 4.81s |
| WASM threads 4→8 | `THREADS_DEFAULT_ISOLATED=8` | embedding 458→约 380ms/批（16 批对比），总导入约 −15% |
| 增量导入跳过未变 chunk | 复用集合时先取 id+source；id 已存在则跳过 embedding/写入/刷新 | 首次 3.16s → 重复导入 **120.6ms**（embed/write/refresh=0） |
| 集合句柄缓存 | `server/src/db/collections.ts` 30s TTL + client/删除/创建失效 | resolve 3.3–4.2ms → 0.01ms；server 请求 5.3→2.5ms |
| length bucketing | embedding 前按文本长度排序分桶 | 本轮同质语料收益不显著；保留用于异构文档 |
| 埋点/基准能力扩展 | bench-browser 支持 `--threads`；matrix 支持 threads；新增优化原始数据目录 | 可复现实验 |

## 5. 行业/前沿方法调研结论（采用/未采用）

1. **ONNX Runtime Web 的 WebGPU EP + WASM SIMD/多线程**：已采用（WebGPU 优先、WASM q8 回退、threads 8），这是端侧 embedding 最直接的加速手段。
2. **量化（INT8/FP16）**：已采用 q8/fp16/fp32；质量门通过；不追求 q4 以免质量风险。
3. **动态批处理与 length bucketing**（Triton/vLLM 等推理服务的常见做法）：已实现简单长度分桶；对同质语料收益有限，后续可按 token 预算做动态批。
4. **内容寻址增量写入**（类似 CDC/幂等 upsert）：确定性 chunk id + 已存在 id 跳过，是重复导入从秒级降至 120ms 的关键。
5. **元数据/集合句柄缓存**（数据库连接池/statement cache 思路）：已落地，实测消除每次查询 ~3–4ms。
6. **索引刷新合并/延后**：seekdb 当前只有全量 `refresh_index`；官方要求刷新后可检索，不能简单跳过。可研究把多次导入的刷新合并到一次、或在后台异步刷新并通知；需保持验收语义。
7. **HNSW 参数调优**（M/ef_construction/ef_search）：seekdb schema 目前用默认参数；数据库检索只有 2ms，收益空间小于刷新成本，暂不作为主优化；可作为质量/延迟调优项。
8. **Web Worker / ORT proxy**：可避免主线程卡顿、改善交互负担；会引入消息/线程开销，当前以吞吐优先，列为后续体验优化。
9. **生产部署同源静态资源/HTTP keep-alive**：查询 HTTP 占 13–20ms（dev 代理）；生产同源可减少代理层，列为后续部署优化。

## 6. 进一步优化空间（未实施，按收益排序）

1. **refresh 成本**：0.6–0.7s 已成为 WebGPU 路径最大项；可做刷新合并/后台刷新（必须保持“刷新完成可检索”）。
2. **WASM 查询小 batch**：query.embed 5–9ms；可复用预分配 buffer/session warmup，收益有限。
3. **HTTP 同源部署**：可减 2–5ms/查询。
4. **Web Worker/ORT proxy**：改善 UI 卡顿，吞吐可能略降。
5. **HNSW/全文参数**：如需更高 Recall 可调 ef_search/M，需重新测质量与延迟。
6. **token 预算动态批**：对真实异构文档比固定长度分桶更优。

## 7. 结论

- 慢的主因是 **WASM embedding（60% 量级）+ 逐文件清理（20%）+ 写入/刷新（20%）**，不是 seekdb 检索本身（2ms 级）。
- 本轮把 q8/WASM 首次导入从 6.93s 降到控制条件 3.56s，重复导入降到 121ms；查询 server 端从 5.3ms 降到 2.5ms；WebGPU 路径首次导入约 1.77s。
- 指标仍需在稳定环境复测；当前报告同时保留中位数/IQR 与原始数据，避免把主机噪声当成算法收益。

## 8. 最终复测（2026-10-27，高优先级、低干扰窗口）

主矩阵改为 4 个官方必需配置（FP32+WASM / INT8+WASM / FP16+WebGPU / 冷启动），用高优先级进程运行，ABBA × 5 轮；数据在 `docs/benchmarks/matrix-2026-10-27/`。控制的消融与增量导入数据在 `docs/benchmarks/optimization-2026-10-27/`。

| 配置 | 导入 p50 | 导入 IQR | 向量化吞吐 | db.search p50 | 查询 e2e p50 | 相对 2026-10-26 基线 |
|---|---|---|---|---|---|---|
| FP32+WASM | 3.06 s | 0.19 s | 56.0 chunks/s | 2.7 ms | 23 ms | 优化前 9.47 s → −67.7% |
| INT8(q8)+WASM | **2.53 s** | 0.09 s | **75.5 chunks/s** | 2.8 ms | **18 ms** | 优化前 6.93 s → **−63.5%** |
| FP16+WebGPU | **1.25 s** | 0.19 s | **485.1 chunks/s** | 2.2 ms | 23 ms | 优化前 3.38 s → −63.0% |
| INT8+WASM 冷启动 | 2.67 s | 0.21 s | 72.4 chunks/s | 2.9 ms | 21 ms | 模型加载另计 453 ms |

- 最终 q8/WASM 阶段拆分：read ~0.06 s、embed 1.65 s、write 0.28 s、refresh 0.50 s、cleanup ~0；总 2.53 s。
- 最终 FP16/WebGPU：read ~0.06 s、embed 0.26 s、write 0.28 s、refresh 0.55 s；总 1.25 s。**refresh 已是最大单项**。
- 最终查询分段（q8/WASM）：query.embed 4.1 ms、query.http 8.2 ms、db.search 2.8 ms、e2e 18 ms；集合 resolve 缓存后几乎为 0。
- 增量导入：首次 3.16 s → 重复导入 **101 ms**（embed/write/refresh 全为 0，仅读取/分块/一次 id 列表）；证据 `optimization-2026-10-27/reimport-result.json`。
- 浏览器质量（当前应用，`quality-browser/`）：q8+WASM R@5 0.5744 / nDCG@10 0.7659，FP16+WebGPU R@5 0.5642 / nDCG@10 0.7652，均 ≥ fp32 基线（0.5642/0.7651），质量门通过。

> §2 中的控制实验值来自不同时间窗口（例如 q8 3.56 s、WebGPU 1.77 s），与 §8 的最终矩阵数值有环境差异；以 §8 和报告 §0 为准。

## 9. 夜间静音模式追加实验（相对比较，不与白天绝对值混用）

> 2026-10-27 夜间用户开启系统静音/低功耗模式，CPU 频率与散热受限，**绝对耗时明显高于白天最终矩阵**。本节只做同一静音窗口内的 A/B 相对比较，不用这些数字替换 §8 的白天基线。

### 9.1 索引刷新是硬语义，不能省

用真实 API 写入 1 条 512d 向量并显式 `refreshIndex=false`，随后用同向量检索：

- 刷新前：`ids=[]`（新向量完全检不到）
- 手动 `refresh` 后：`ids=["probe-1"]`（立即可检索）
- 单条刷新仍耗时约 821 ms

结论：seekdb 的 HNSW 索引必须 `refresh_index` 后才可见，不能通过“跳过刷新”换性能；只能优化刷新次数/时机。

### 9.2 已采用：陈旧块删除时合并刷新（少一次全量刷新）

旧路径在“复用集合 + 文件变短/改写”时：写末批刷新一次，清理删除陈旧块后再刷新一次，共两次全量刷新。
新路径提前计算 stale ids；若本次会删除，则**推迟写末批刷新**，清理删除后只刷新一次；若清理实际未删除（删除失败），兜底补刷新，保证新写入可检索。

真实浏览器 e2e（`optimization-2026-10-27/stale-refresh-e2e.json`）：

| 场景 | read | embed | write | cleanup | refresh | total |
|---|---|---|---|---|---|---|
| 首次导入 3 chunks | 38.4 ms | 147.7 ms | 658.6 ms | 0 | 606.0 ms | 976.8 ms |
| 改写 alpha.md 后重导（1 stale） | 6.3 ms | 6.7 ms | 26.0 ms | 21.2 ms | **502.8 ms（仅 1 次）** | 736.0 ms |
| 再导入完全相同的文件 | 2.5 ms | 0 | 0 | 0.005 ms | **0** | 38.0 ms |

- 改写重导后最终 count=2、检索 2 hits 且 alpha 新内容命中；陈旧块不返回。
- 旧路径在第二行会多一次约 0.5 s 的全量刷新；新路径只付一次。
- 该项不影响“新建集合首次导入”主矩阵，只优化连续导入/文件改写场景。

### 9.3 已实验但否决：embedding 与写入流水线重叠

对 q8/WASM 同一静音窗口做 A/B（顺序实现 vs 写入-embedding 重叠）：

| 实现 | ingest p50 | doc.embed p50 | doc.write p50 |
|---|---|---|---|
| 顺序（保留） | **2.843 s** | 491.5 ms | 84.8 ms |
| 写入与下一批 embedding 重叠 | 3.047 s（慢 7%） | 567.2 ms | 582.1 ms |

原因：本机 WASM 推理占满 CPU，while 下一批 embedding 运行时，HTTP/DB 写入被 CPU 抢占，写入尾延迟拉长，反而拖慢总时长。该实现已回退，不进入交付代码；WebGPU 路径未完成同条件 A/B，也不冒险启用。

### 9.4 已实验但否决：BGE 检索指令前缀

BGE 常建议 query 指令 “为这个句子生成表示以用于检索相关文章：”。在 Node 质量回归、同一数据/量化下：

| 方案 | q8 Recall@5 | q8 nDCG@10 | fp32 Recall@5 |
|---|---|---|---|
| 无前缀（当前默认） | **0.5682** | **0.7532** | 0.5606 |
| 加 BGE 检索指令 | 0.5260（−4.2pp） | 0.7281（−0.025） | 0.5536 |

结论：本数据集上指令前缀显著掉点，**不采用**；保持当前查询/文档同分布编码。

### 9.5 当前保留的改动

- 保留：陈旧块刷新合并（§9.2），有真实 e2e 与后端语义实验支撑。
- 回退/不采用：写入流水线（§9.3）、检索指令前缀（§9.4）。
- 白天最终矩阵与质量数字仍以 §8 / 报告 §0 为准；夜间数字仅用于相对判断。

### 9.6 已实验但否决：并行 FileReader 读取/分块

同一静音窗口内对比顺序读取与 8 路并发 FileReader（q8/WASM，120 文件）：

| 实现 | doc.read p50（单文件） | 每轮 readMs（5 轮） | 结论 |
|---|---|---|---|
| 顺序读取（保留） | **1.3 ms** | 291 / 237 / 191 / 128 / 229 ms | 低开销 |
| 8 路并发读取 | 7.0 ms | 1347 / 883 / 804 / 960 / 690 ms | 明显更差，回退 |

原因：浏览器的 FileReader/Blob 读取在渲染进程内并不具备真正的并行收益，反而引入调度与内存竞争；`doc.read` 单项已证明变差。总导入时间因静音模式功耗漂移有波动，因此不采用该实现。证据：`optimization-2026-10-27/read-concurrency-{sequential,parallel}.md`。

> 结论：本轮只保留有同窗口证据支撑的改动；禁止用“看起来可并行”的直觉替换已验证路径。

## 10. 严格复核（同静音窗口，ABBA/交错）

> 本节纠正一个容易犯的错误：不能把“组合收益”全部归因于某一个参数。以下全部为同一静音窗口内的交错 A/B，绝对耗时不可与白天矩阵比较。

### 10.1 batch / WASM threads 的严格消融

3 轮 ABBA 消融（q8/WASM，120 chunks，ingest.total p50）：

| 配置 | 跨调用 ingest p50 | 结论 |
|---|---:|---|
| batch16 / threads8 | 3070.3 ms | 与 32 差距很小 |
| batch32 / threads8 | 3121.8 ms | 当前默认 |
| batch48 / threads8 | 3112.4 ms | 无进一步收益 |
| batch64 / threads8 | 3142.4 ms | 无进一步收益，且大 SQL 有超时风险 |
| batch32 / threads4 | 3747.9 ms | **慢约 20%**；threads 4 明显不足 |
| batch32 / threads2 | 6030.4 ms | 慢近一倍，禁用 |

再对 batch16 vs 32 做 5 轮 ABBA：b16 3237.6 ms、b32 3133.0 ms，**b32 约快 3.2%**。

结论：**线程数 8 是明确收益（约 20%）**；batch 16→32 只有约 2–3% 的小幅收益；batch48/64 无收益且增加 DB 大 SQL 风险。保留 batch32/threads8，但技术说明中不再把导入 −63.5% 全部归因于 batch/threads（清理批量化、单次刷新、增量跳过等共同贡献）。

### 10.2 embedding padding：字符排序无效，UTF-8 字节排序有效

用真实 tokenizer 统计 120 chunks（88–119 tokens），模拟不同排序 key 的 batch padding：

| batch | 原始 padding | 按字符长度 | 按 UTF-8 字节 | 按 token（上限） |
|---:|---:|---:|---:|---:|
| 16 | 10.48% | 8.97%（仅 −1.36%） | **3.83%（−6.02%）** | 1.44%（−8.18%） |
| 32 | 11.98% | 10.35%（仅 −1.46%） | **4.71%（−6.50%）** | 3.45%（−7.62%） |

结论：原实现的 `text.length`（UTF-16 字符）排序，对中文/英文混合语料几乎没有作用；**UTF-8 字节长度是几乎零成本且接近 token 排序的代理**。已将排序 key 从字符长度改为 UTF-8 字节长度（`paddingBucket: 'utf8-bytes'`）。

同窗口交错 A/B（3 轮/次，前后各两次）：

| 实现 | doc.embed p50 | ingest.total p50 |
|---|---:|---:|
| 字符排序（旧） | 528.6 / 541.8 ms | 3133.6 / 3036.9 ms |
| **UTF-8 字节排序（新）** | **508.9 / 492.0 ms** | **3006.7 / 3037.2 ms** |
| 中位数变化 | **约 −6.5% embedding** | **约 −2.1% 导入** |

证据：`optimization-2026-10-27/padding-sim.json`、`byte-sort-ab-{char,byte}-{1,2}.md`。

### 10.3 当前最终保留

- 线程8/batch32：线程收益明确，batch32 小幅优于 16；batch48/64 不采用。
- UTF-8 字节长度分桶：保留；字符分桶实现被替换。
- 陈旧块刷新合并：保留（§9.2）。
- 写入流水线、并行 FileReader、BGE 指令前缀：均实测否决，不进入交付代码。

### 10.3 集合句柄缓存失效验证

缓存不是“无条件缓存”，代码包含 client 代际检查、30s TTL、创建/删除主动失效。用真实 API 验证：

1. 创建 512d 集合、写入 1 条、连续检索：`resolveMs` 首次 0.01ms（缓存命中）；
2. 通过 API 删除同名集合，重建为 **384d 英文集合**；
3. 重建后首次检索：`resolveMs=4.94ms`（缓存未命中，重新 describe），返回 384d 新句柄，没有出现旧 512d 句柄导致的维度错误。

结论：删除/重建路径缓存失效正确；连接重建时缓存 key 绑定 client 实例，旧句柄不会跨连接复用。该结论来自本机实测，不是仅靠代码推断。

### 10.4 归因边界

- 36–63% 的导入改善来自多项组合：清理批量化、线程 8、单次刷新/刷新合并、增量跳过、UTF-8 字节分桶。
- 同窗消融可确认：threads8 约 −20%；batch32 对16 约 −3%；UTF-8 字节分桶 embedding 约 −6.5%。
- 不能把组合收益全部归因于 batch/threads；技术说明/报告已按此口径修正。

### 10.5 故障注入：seekdb 停机 → 503 → 重启同会话恢复

真实浏览器 e2e 操作序列（`optimization-2026-10-27/failure-injection.json`）：

1. 启动时 `health?deep=1` 正常；
2. `docker stop seekvec-seekdb`；
3. 浏览器提交导入：失败，返回 **HTTP 503 `SEEKDB_UNAVAILABLE`**（不是 500）；
4. 立即第二次提交：仍 503，但错误不是“已有导入任务”，说明 busy 已正确释放；
5. `docker start seekvec-seekdb`，健康检查恢复；
6. 同一页面、同一会话再次导入：成功；随后检索命中新导入文档（hits=1，e2e 30ms）。

根因修复：seekdb SDK 外层包成 `SeekdbConnectionError`，真正的 `ECONNREFUSED` 在 `error.cause.code`；原 `isConnectionError` 只看外层 message，导致错误映射 500 且不重试。现在递归检查 `message/name/code/cause`，并补了单测。

同时修掉刷新合并引入的 false-success：清理后的刷新失败不再只 `console.warn` 后返回成功，而是最多重试一次，仍失败则抛错，避免“导入成功但新数据不可检索”。

### 10.6 最终默认：WASM 线程按硬件自适应

5 轮 ABBA（q8/WASM，batch=32，其他条件不变）：

| threads | ingest.total p50 | doc.embed p50（每批） | 查询 e2e p50 |
|---:|---:|---:|---:|
| 8 | 2804.2 ms | 460 ms | 24.3 ms |
| 12 | 2597.4 ms | 392 ms | 27.0 ms |
| 14 | 2551.9 ms | 约 365 ms | 25.8 ms |
| **16** | **2411.2 ms** | **约 348 ms** | 25.0 ms |

结论：28 核上 16 线程比 8 线程导入 **−14.0%**，embedding **约 −24%**；但低核机器不能照搬 16。实现改为：

```text
threads = min(cores, 16, max(8, ceil(cores * 0.6)))   // crossOriginIsolated 时
```

- 28 核 →16、16 核→10、8 核→8、4 核→4、2 核→2；`?threads=` 显式覆盖。
- 实际页面验证：默认运行生效配置为 `threads=16`，q8/WASM 导入 2413ms（静音窗口）。
- 白天最终主矩阵仍固定 `threads=8`，用于与历史数据可复现对比；默认值改自适应后，严格评测直接运行应用会使用 16（本机）。
- 该改动不改变 WebGPU 路径与查询语义；单测新增 28/16/8/4/2 核映射覆盖。

证据：`optimization-2026-10-27/threads-5run-matrix-summary.md`、`adaptive-threads-default.{md,raw.json}`。

### 10.7 模型/集合切换状态 e2e

真实页面操作（`optimization-2026-10-27/state-switch-e2e.json`）：

1. 导入集合 A（中文，ALPHA-UNIQUE），再导入集合 B（中文，BETA-UNIQUE）；activeCollection 自动切到 B；
2. 检索 BETA-UNIQUE：命中集合 B，hits=1；
3. 点击“英文”模型：旧结果被清空；中文集合与新模型不兼容，回退/空集合提示路径生效；
4. 英文模型就绪后切回“中文”，集合下拉重新回填；
5. 选择集合 A，检索 ALPHA-UNIQUE：命中 A，hits=1。

修复点：`useSearch` 原先只在 modelKey 变化时清空结果；现在 `activeCollection` 变化也会清空，避免切集合后界面残留上一集合结果。模型/集合/运行时的维度与 activeCollection 回退逻辑由 `collectionSelection` 纯函数与 `useCollections` 负责，已有 10 项单测。

### 10.8 刷新失败精确注入（请求拦截）+ 跨 reload 补刷新

用 Puppeteer 拦截 `POST /api/collections/<name>/refresh` 并 abort，构造“写入/清理成功但 refresh 失败”：

1. 首次导入 V1（2 chunks）成功；
2. 改写为 V2 后导入，拦截所有 refresh 请求（阻断 3 次：清理重试 2 次 + 失败补偿 1 次）；
3. 导入明确失败：`清理后索引刷新失败，无法保证本轮新增/删除数据可检索`；
4. 立即再次导入：失败原因是 `补刷新失败...`，**不是**“已有导入任务”，说明 busy 已释放；
5. **刷新页面**（runtime/内存状态清空）；
6. 解除拦截后重试同一 V2 文件：`embed/write=0`，但触发 **补刷新 refreshMs≈102ms**（dirty 标记从 localStorage 恢复），随后检索命中。

实现：`pendingRefresh` per-collection 脏标记，持久化到 `localStorage('seekvec:pendingRefresh')`；refresh 成功清除，失败/补偿失败保留。避免“重试内容完全相同 → 无变化 → 永不刷新”的隐性不可检索。

### 10.9 外部删除集合后的 store 同步

`useCollections` 原来只“增量注册”集合，server 删除的集合会在前端 store 残留，activeCollection 可能指向幽灵集合并触发 404。修复：新增 `kbStore.syncCollections(list)`，server 回填时**整体替换** collections/counts。

真实 e2e（`optimization-2026-10-27/collection-sync-e2e.json`）：

1. 导入集合 A/B，A/B 均在下拉中；
2. 通过 server API 外部删除 A（不经过前端）；
3. 触发模型切换 → `useCollections` 重新拉取并 sync；
4. 结果：`hasA=false`、`hasB=true`，A 从 store/下拉消失；active 回退到可用集合，检索可继续。

该修复针对评测清理/外部维护场景，防止幽灵集合造成 404 或展示过期集合。

### 10.10 同集合跨后端切换（WASM → WebGPU → WASM）

真实页面 e2e（`optimization-2026-10-27/cross-backend-e2e.json`）：

1. WASM/q8 导入集合 A 并检索：hits=1，`backend=wasm`；
2. 重新加载页面 `?backend=webgpu&dtype=fp16`，activeCollection 恢复，同集合检索：hits=1，`backend=webgpu`；
3. 再切回 WASM/q8：hits=1，`backend=wasm`。

结论：模型/后端切换后集合与 activeCollection 状态可恢复，同一切量集合跨后端可检索；不同后端 embedding 同维度/同向量空间，不产生集合不兼容。运行时 pipeline cache 仍按 modelKey:backend:dtype 隔离。

### 10.11 规模边界（600 / 1200 文档）

用临时复制语料（语义重复，仅测规模/超时边界；不进入质量口径）：

| 规模 | chunks/批次 | ingest total | embed/批 | write/批 | refresh | query e2e |

### 10.12 长导入期间 UI 并发保护

|---|---|---|---|
| 导入中（reading/embedding/writing） | disabled | disabled | disabled |

实现：`ModelBadge` 在 `kbStore.ingestStatus` 为 reading/embedding/writing 时禁用模型切换；`SearchPanel` 同时禁用集合下拉和检索按钮，避免长导入中切换 activeCollection/运行时。

### 10.13 可取消长导入

长任务（1200 文件，~17s）以前只能等待。新增 `cancelIngest()` + UI “取消导入”按钮：

- 模块级 `AbortController`；在读取/embedding/写批/清理/补刷新/计数阶段检查 abort；
- 不强行中断已发出的 HTTP 写请求，避免把“已提交但响应未知”变成不确定状态；
- 取消后若已有批次写入，仍执行补偿刷新；busy 在 finally 释放，状态回 idle；
- UI 控件恢复，可立即重试。

e2e（`optimization-2026-10-27/cancel-ingest-e2e.json`）：

1. 启动 1200 文件导入，取消按钮出现；
2. 点击取消：promise 以“导入已取消”结束；
3. 模型控件恢复（modelDisabled=false）、取消按钮消失；
4. 重新导入 1 个文件成功，检索 hits=1。

说明：错误文案的 UI 渲染与检查存在 React 异步批处理时序；任务退出/资源释放/重试能力已由 e2e 验证。

### 10.14 取消竞态：在 writing 阶段取消

不只测早期取消，而是用 1200 文件导入并轮询到页面显示“正在写入 SeekDB”后再点“取消导入”：

- `writingSeen=true`；
- 取消后导入 promise 以 `导入已取消` 结束；
- 模型控件恢复（`modelDisabled=false`）、取消按钮消失；
- 已写入批次由失败补偿 refresh 处理；随后重试导入成功，检索 hits=5。

证据：`optimization-2026-10-27/cancel-writing-e2e.json`。说明：部分写入时取消不能回滚已提交事务，但会补偿刷新保证已提交数据可检索；UI 不展示“导入成功”。

### 10.15 取消后页面刷新再恢复

600 文件导入在集合创建前取消，随后刷新页面：

- 取消 promise：`导入已取消`；
- reload 后页面正常加载，模型/集合状态重建；
- 重新导入 1 个文件成功，集合在 `/api/collections` 中出现，检索 hits=1；

结论：取消是进程内瞬时状态，不要求保留“取消记录”；刷新后以 server 集合事实源恢复即可，未出现半初始化死锁。证据：`optimization-2026-10-27/cancel-reload-e2e.json`。

### 10.17 在途检索结果守卫（并发一致性）

检索是异步的；请求返回时模型/集合可能已切换，旧响应不能覆盖新状态。核心判定抽成纯函数：

`shouldAcceptSearchResult({requestId,currentRequestId,modelKey,currentModel,collectionName,currentCollectionName})`

只有**请求代次、模型、集合**三者都未变化才接收结果；`useSearch` 在 await 返回后调用该守卫，模型或 activeCollection 变化时丢弃旧响应。

单测 5 项覆盖：
- 全未变 → 接收；
- 模型已切 → 丢弃；
- 集合已切 → 丢弃；
- 已有更新请求 → 丢弃；
- 旧集合失效（null） → 丢弃。

> 说明：曾尝试用 Puppeteer 挂起 `/api/search` 后切模型做 UI 时序验证，但实测记录显示检索请求实际在切换后才开始，测试时序无效；因此改用确定性纯函数单测，不把无效 e2e 当证据。

### 10.18 检索 HTTP 真正可取消

此前只在响应返回后丢弃旧结果；请求仍会跑完，白占网络/DB。现在：

- `db/api.search` 接受 `AbortSignal`，`request` 用 `AbortSignal.any` 合并调用方取消与 60s 超时；
- `runTextSearch` 在 embedding 后、发 HTTP 前检查 abort；`search` 收到 signal；
- `useSearch` 维护 `AbortController`：新查询、模型切换、集合切换都会 abort 旧控制器；
- 用户取消（AbortError）不显示为错误；真正超时仍显示超时文案；
- 保留上一轮的纯函数 `shouldAcceptSearchResult` 作为二次守卫。

smoke 验证（120 chunks，1 轮）：正常检索未回归，`db.search=3.6ms`、query e2e=27ms。
