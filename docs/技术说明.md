## 1. Embedding 模型来源与量化方案

| 模型 | HuggingFace 来源 | 维度 | 量化 | 实测 ONNX 体积 | 压缩比 |
|---|---|---|---|---|---|
| 中文（默认）| [Xenova/bge-small-zh-v1.5](https://huggingface.co/Xenova/bge-small-zh-v1.5) | 512 | int8（q8）| 22.9 MB（fp32 90.5 MB）| ≈3.95x |
| 英文（可选）| [Xenova/all-MiniLM-L6-v2](https://huggingface.co/Xenova/all-MiniLM-L6-v2) | 384 | int8（q8）| 21.9 MB（fp32 86.2 MB）| ≈3.94x |
| 图片（v1.1）| [Xenova/clip-vit-base-patch32](https://huggingface.co/Xenova/clip-vit-base-patch32) | 512 | int8（q8）| 未启用/未实测 | — |

- 均为 Xenova 仓库的 ONNX 量化版（Apache-2.0 / MIT），通过 Transformers.js v3 `pipeline('feature-extraction', ..., { dtype: 'q8' })` 加载
- 体积为仓库内 `onnx/model_quantized.onnx`（q8）与 `onnx/model.onnx`（fp32）实测文件大小；压缩比 = fp32/q8
- 浏览器端统一 `pooling:'mean' + normalize:true`，输出 L2 归一化向量

### 实测（`npm run bench`，Node CPU EP）

环境：Windows，Node 24，10 条中英混合语料，留一法（每条语料作 query、其余 9 条作候选）；模型已缓存后运行。
命令（本机网络需要镜像时）：

```powershell
$env:HF_ENDPOINT="https://hf-mirror.com/"
$env:SEEKVEC_CACHE_DIR="<repo>\scripts\.cache"
npm run bench
```

| 模型 | q8 加载 | int8 推理（10 条）| fp32 加载+推理 | int8 vs fp32 平均余弦 | Top-1 一致率 | Top-5 重合率 |
|---|---|---|---|---|---|---|
| all-MiniLM-L6-v2 | 139 ms | 22 ms | 161 ms | 0.9870 | 90.00% | 98.00% |
| bge-small-zh-v1.5 | 73 ms | 20 ms | 157 ms | 0.9900 | 100.00% | 94.00% |

- 首次运行需下载权重（q8 约 3–4 s/模型，fp32 更久）；表中为缓存后数据
- 候选集只有 9 条，Top-k 指标仅用于「int8 与 fp32 排序一致性」参考，不等价于真实业务召回率
- 结论：q8 与 fp32 平均余弦 ≥0.987，Top-1 一致率 90%–100%，量化掉点很小（无标注数据集，不虚构绝对召回率）

## 2. SeekDB 使用方式

### 启动 seekdb（三选一）

```powershell
# A. Docker（Windows 推荐；数据卷必须挂 /var/lib/seekdb 才能持久化）
docker volume create seekvec_seekdb-data
docker run -d --name seekvec-seekdb -p 2882:2881 `
  -v seekvec_seekdb-data:/var/lib/seekdb `
  -e REPORTER=seekvec-seekdb quay.io/oceanbase/seekdb:latest
$env:SEEKDB_PORT="2882"; npm run dev

# B. Windows MSI：管理员安装后
cd "C:\Program Files\seekdb\bin"; .\seekdb_manage.ps1 install; .\seekdb_manage.ps1 start

# C. Linux/macOS 嵌入式
export SEEKDB_PATH=/path/to/seekdb/data
```

**版本对齐**：项目依赖 seekdb-js `1.3.0`（server 端 `seekdb@1.3.0`，peer 依赖用 `.npmrc` 的 `legacy-peer-deps=true` 绕过上游 `@seekdb/default-embed` 的 workspace 缺陷）。实测 1.3.0 SDK 与 seekdb server **1.4.0**（Docker 镜像）完全兼容；Windows 嵌入式不受官方支持，本项目拒绝该组合。

### 集合结构（双集合架构）

| 集合 | Schema |
|---|---|
| `kb_text_zh` | `VectorIndexConfig(HNSW, dim=512, cosine)` + `FulltextIndexConfig('ik', ik_mode='smart')` |
| `kb_text_en` | `VectorIndexConfig(HNSW, dim=384, cosine)` + `FulltextIndexConfig('ik', ik_mode='smart')` |
| `kb_image`（v1.1）| `VectorIndexConfig(HNSW, dim=512, cosine)`，无 fulltext |

`embeddingFunction: null` —— 向量由 web 端推理产出后经 HTTP 写入，server 不调用任何 embedding 库，严格满足规则 1「端侧运行」与规则 6「禁止伪装端侧实则走远程」。

集合写入前会校验：已存在集合的实际维度/模态必须与请求模型一致（否则 409）；每条向量的长度必须等于集合维度（否则 400）。

### 检索方式：向量 + 全文混合检索

```ts
// 纯向量检索（1.3.0 query() 无 knn 键）→ 返回 distances（cosine，越小越相关）
result = await collection.query({
  queryEmbeddings: [queryEmbedding],
  nResults,
  include: ['documents', 'metadatas', 'distances'],
});

// 混合检索（RRF 在 SeekDB 库内完成）→ 返回 scores（RRF 融合分，越大越相关）
result = await collection.hybridSearch({
  query: { whereDocument: { $contains: keyword.trim() } },
  knn: { queryEmbeddings: [queryEmbedding] },
  nResults,
  include: ['documents', 'metadatas', 'distances'],
});
```

- RRF 由 SeekDB 的 `DBMS_HYBRID_SEARCH` 在库内合并，业务侧只取最终 top-k（满足「非客户端拼合」）
- 两种模式分数语义相反：server 显式拆成 `scores` / `distances` 返回，前端按 metric 分别展示（混合检索显示「RRF 融合分」，纯向量显示「相似度 = 1 - distance」）

### 索引刷新与写入

- 写入使用 `collection.upsert(...)`：chunk id 由「文件名+块序号+文本」hash 生成，同一文件重复导入是幂等覆盖（实测两次完整导入后条目数不变）
- 索引刷新策略：批量导入时除最后一批外均传 `refreshIndex=false`，**只在最后一批调用一次 `refresh_index()`**，减少刷新次数
- 批量大小：端侧 embedding 16 条/批；HTTP 写入同批

### HTTP API 概览

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/collections` | 列举集合（含维度、模型 key、条目数），供前端刷新后恢复状态 |
| POST | `/api/collections` | 建集合（按模型选择 dimension 与 ik_mode；已存在则校验兼容性）|
| POST | `/api/documents` | 文本批量入库（upsert，支持中间批次跳过索引刷新）|
| POST | `/api/images` | 图片向量批量入库（v1.1 预留）|
| POST | `/api/search` | 向量 / 混合检索（返回 distances 或 scores）|
| GET | `/api/documents/:name/count` | 集合条目数 |
| GET | `/api/health` | 健康检查 |

连接韧性：seekdb 服务/容器重启后，首个请求会自动重建连接并重试一次，dev server 无需重启。

## 3. 后端选择与降级策略

```
启动 → navigator.gpu.requestAdapter()
        ├─ 成功 → WebGPU
        └─ 失败 / 不支持 → WASM
                ├─ 启动探测
                └─ pipeline 初始化失败 → 运行时自动切 WASM 并重试一次
```

| 触发条件 | 行为 |
|---|---|
| 浏览器不支持 WebGPU / adapter 请求失败 | 启动期直接选 WASM，徽标显示「WASM」|
| pipeline 初始化报错（资源分配、模型下载失败等）| `loadModelWithFallback` catch 后切 WASM 重试；缓存键为 `modelKey:backend`，失败 Promise 会被移除，重试不会命中坏缓存 |
| 模型加载失败 | 导入/检索面板显示错误原因 + 「重试」按钮 |
| WASM 多线程 | dev 与 preview 均注入 `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`，启用 SharedArrayBuffer |
| ORT wasm 资源 | 默认走 jsDelivr CDN；可用 `VITE_ORT_WASM_PATH` 指向本地托管（如 `/ort/`），离线环境可用 |
| 模型下载源 | 默认 huggingface.co；可用 `VITE_HF_ENDPOINT` 切换镜像，或 `VITE_LOCAL_MODELS=1` 使用本地模型目录 |

UI 提示：`BackendBadge` 显示「WebGPU（绿色）」或「WASM（琥珀色 + 降级原因）」，title 中附带模型加载耗时。
实测：Chromium 无头环境 WebGPU 上下文创建失败时成功降级 WASM 并完成导入/检索；强制 WASM 路径同样通过端到端验证。

## 4. 状态管理与优化点

### 状态管理（Zustand 4 个 store）

| Store | 内容 |
|---|---|
| `modelStore` | 当前模型 key 与维度 |
| `backendStore` | 当前后端 + 降级原因 + 模型加载耗时 |
| `kbStore` | 集合清单、文档计数、ingest 进度/状态 |
| `searchStore` | query、keyword、文本/图片结果、检索错误 |

刷新恢复：`useCollections` 在启动时调用 `GET /api/collections` 回填 `kbStore` 与计数 —— 修复了「刷新后集合清单丢失、检索静默无结果」的问题；切换模型时会同步默认集合名并清空旧结果。

### 优化点

| 优化 | 实现 |
|---|---|
| 批处理 | embedding 推理 16 条/组；HTTP 写入同批次 |
| 索引刷新 | 导入过程只在最后一批刷新一次索引（`refreshIndex=false` 中间批次）|
| 幂等导入 | 确定性 chunk id + server `upsert`，重复导入同一文件不产生重复分块 |
| 检索延迟 | 分段计时：端侧向量化耗时 `embeddingMs` + HTTP/DB 检索耗时 `latencyMs`，检索面板实时展示 |
| 模型加载 | 模型按 `modelKey:backend` 懒加载缓存；加载耗时写入 `backendStore` 并在徽标 tooltip 展示 |
| 状态恢复 | 启动时列举集合回填，集合维度/模态与模型不匹配时明确提示 |
| 容错 | 连接自动重连；ingest 失败状态可恢复并可重试；检索异常展示错误而非静默 |
| 错误的前端面 | 无集合 / 维度不匹配 / 模型加载失败 / 检索失败均有可见提示 |

实测（本机 Docker Desktop + Chromium WASM/WEBGPU）：语义检索 14–41 ms/次，混合检索 124–145 ms/次（含 HTTP + Docker 内 seekdb），端侧 query 向量化约 5–10 ms/条，模型缓存后加载约 0.3–0.4 s。

## 5. 交付与启动

```powershell
npm run install:all      # 安装 根+server+web+scripts 依赖
npm run dev              # predev 检查 seekdb；同时拉起 server + web
npm run probe            # seekdb 端到端探针
```
